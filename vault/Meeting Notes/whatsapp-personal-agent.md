# סוכן WhatsApp אישי (WAHA + Outlook + חשבוניות)

## Overview
פרויקט עצמאי (לא קשור לצוות התוכן יעל/יובל/חן/נועה) — מטרתו לתת ל-Claude Code יכולת לשלוח ולקבל הודעות WhatsApp בשם המשתמש (אלעד), ובהמשך לבנות סוכן שיחתי מלא בוואטסאפ (כולל הקלטות קול) שיתפעל גם Outlook (מיילים + יומן) וגם הוצאת חשבוניות (חיבור לנועה/webenefit-invoice הקיימים).

**שלב 1 (שליחה בסיסית) — הושלם ועובד.** שרת [WAHA](https://waha.devlike.pro) (WhatsApp HTTP API לא-רשמי, מנוע NOWEB) רץ ב-Docker על שרת Hetzner Cloud ייעודי (CX23, Falkenstein, IP `188.245.198.72`), עם WhatsApp האישי של אלעד (`972542438624`) מקושר בפועל. Claude מתחבר ב-SSH ישירות לשרת ומריץ `curl` מול ה-API המקומי (`127.0.0.1:3000`, מוגן ב-API key) כדי לשלוח הודעות.

**שלב 2, תת-פרויקט #1 (קליטת הודעות בלבד, בלי לוגיקת תגובה) — הושלם ועובד.** שירות `inbox/` (Hono+TypeScript+`node:sqlite`) רץ כ-container שני לצד `waha` על אותו שרת Hetzner, קולט webhook מ-WAHA לצ'אט הייעודי ("הודעה לעצמי") ושומר ל-SQLite. מה עושים עם ההודעות שנקלטו — עדיין לא הוחלט, בכוונה (ראה Open Questions). שאר שלב 2 (לוגיקת תגובה, תמלול קול, Outlook, חשבוניות) עדיין בגדר תכנון.

קבצי הפרויקט בריפו: `waha/` (docker-compose + .env.example), `inbox/` (שירות הקליטה, חדש), `whatsapp-inbox/` (סקלטון Next.js ריק, לא בשימוש — הוחלף בפועל בגישת `inbox/` על אותו שרת Hetzner, לא Vercel).

## Open Questions
- **תמלול הקלטות קול** — יידרש שירות transcription (Whisper API או דומה) לטיפול בהודעות קוליות בוואטסאפ. **הסיווג של הודעה קולית ב-`inbox` עדיין לא אומת מול הקלטה אמיתית** (2026-08-09: המשתמש שלח הקלטת בדיקה שלא הגיעה לצ'אט הנכון / לא נקלטה בפועל, ובחר לדחות את הבדיקה להמשך). הלוגיקה כתובה לפי `hasMedia`+`media.mimetype` (מבוסס על טקסט אמיתי בלבד שאומת) — צריך הרצת בדיקה חיה עם הקלטה אמיתית לפני הסתמכות עליה.
- **WAHA מוריד ושומר קבצי מדיה אוטומטית בשרת** (נצפה בלוגים: "has media, downloading it... has been saved") — **סוטה מהעיצוב המקורי** של `inbox` ("לא מורידים קובץ שמע בשלב הזה"). ה-`inbox` עצמו לא מוריד כלום, אבל WAHA/המנוע עושה את זה ברמת התשתית בלי קשר. לא הוחלט אם/איך לחסום את זה (יש הגדרות WAHA לבקרת auto-download של מדיה, לא נבדקו).
- **אינטגרציית Outlook (Microsoft Graph API)** — חסומה: למשתמש אין (או הוא לא בטוח שיש לו) גישת אדמין ל-Azure/Microsoft 365 לרישום App Registration. צריך לבדוק אם חשבון Microsoft אישי (לא בהכרח tenant admin) יכול לרשום אפליקציה בעצמו ב-Entra ID — סביר שכן, לא נבדק בפועל.
- **זרימת אישור לחשבוניות דרך WhatsApp** — נועה (agent-noa) מחייבת טיוטה + אישור מפורש מהמשתמש לפני קריאה אמיתית ל-WeBenefit. איך זה עובד כשההפעלה מגיעה מהודעת WhatsApp (הקלטה/טקסט)? לא הוחלט — צריך מנגנון אישור (תשובת "כן"/"אשר" בצ'אט?) שלא עוקף את דרישת האישור המפורש.
- **קוד/סוכן שמריץ את "השיח"** — כרגע Claude Code (הסשן הזה) הוא מי ששולח הודעות ידנית לפי בקשה. בשלב 2 צריך תהליך אוטונומי-משהו שרץ ברקע ומגיב לבד — טרם הוחלט אם זה Claude Agent SDK רץ כשירות, polling תקופתי, או משהו אחר.
- **גיבוי/ניקוי סיסמת root הזמנית** — נקבעה סיסמת root זמנית (`roothetzner2026`-סטייל) בשרת כדי לעקוף באג מקלדת בקונסולת הדפדפן של Hetzner; login בסיסמה כבר בוטל ב-`sshd_config` (`PasswordAuthentication no`), אבל **הסיסמה עצמה עדיין מוגדרת בפועל בחשבון ה-root** (`passwd`) — לא נדרשת עוד כי SSH דורש מפתח, אבל שווה לשנות אותה למשהו רנדומלי בעתיד כניקיון (לא קריטי כי `PasswordAuthentication no` חוסם שימוש בה מרחוק).

### 2026-08-09 — שלב 2 תת-פרויקט #1: שירות קליטת הודעות (`inbox`), עיצוב מלא ופריסה חיה [shipped]
- **What was done:** תהליך brainstorming מלא לשלב 2 — זוהה שהבקשה המקורית ("סוכן שיחתי + Outlook + חשבוניות") מכילה 4 תת-מערכות עצמאיות; המשתמש אישר פיצול ובחר לצמצם את #1 לקליטה בלבד (בלי לוגיקת תגובה). נכתב spec ([docs/superpowers/specs/2026-08-09-whatsapp-inbox-capture-design.md](../../docs/superpowers/specs/2026-08-09-whatsapp-inbox-capture-design.md), בעברית לפי בקשת המשתמש) ותכנית מימוש בת 6 משימות ([docs/superpowers/plans/2026-08-09-whatsapp-inbox-capture.md](../../docs/superpowers/plans/2026-08-09-whatsapp-inbox-capture.md)), בוצעו ב-subagent-driven-development (implementer + spec-review + code-quality-review לכל משימה, ישירות על main באישור מפורש של המשתמש). נבנה שירות `inbox/` (Hono+TypeScript) עם 14 טסטים (Vitest), שני קונטיינרים ב-`waha/docker-compose.yml` (`waha`+`inbox`, `inbox` בלי port חשוף — רק ברשת דוקר פנימית).
- **סטיה מהתכנית שהתגלתה תוך כדי מימוש:** `better-sqlite3` (מתועד ב-spec המקורי) נכשל להתקין על Node 24 (אין prebuilt, Python תקול במחשב המשתמש) — הוחלף ב-`node:sqlite` המובנה של Node עצמו (Node 22.5+, בלי native build), אומת ידנית שה-API תואם לפני שבוצע השינוי. עודכן ב-spec ובתכנית.
- **4 בעיות production שהתגלו ותוקנו רק בפריסה חיה מול WAHA האמיתי (לא נתפסו ב-unit tests, כי דרשו payload אמיתי):**
  1. אירוע ה-webhook הנכון הוא `message.any`, לא `message` (`message` הוא incoming בלבד, לא כולל הודעות שנשלחו על ידינו).
  2. **chat id מגיע תמיד מ-`payload.from`, לעולם לא מ-`payload.to`** — ל-`to` אין קיום בפועל בפיילוד כלל. ההנחה המקורית (`fromMe ? to : from`) הייתה שגויה ודחתה בשקט כל הודעה יוצאת.
  3. **אין שדה `type` בפיילוד האמיתי של מנוע NOWEB בכלל** — הסיווג טקסט/מדיה נעשה לפי `hasMedia`+`media.mimetype`, לא לפי מחרוזת `type` כמו `'chat'`/`'ptt'` (שהיו הנחה שגויה, כנראה ממנוע אחר של WAHA). כל שלושת הבאגים אותרו ע"י לוג דיבאג זמני שנוסף/הוסר תוך כדי (לא נשאר בקוד המסופק).
  4. **session קיים ("default") לא קלט את `WHATSAPP_HOOK_URL`/`WHATSAPP_HOOK_EVENTS` הגלובליים מה-env באופן רטרואקטיבי** — הצריך `PUT /api/sessions/default` מפורש עם `config.webhooks` כדי לעבוד; sessions חדשים בעתיד יקבלו את זה מה-env כברירת מחדל.
- **תופעת לוואי שנצפתה ותועדה (Open Questions):** WAHA מוריד ושומר קבצי מדיה בשרת אוטומטית ברמת המנוע, בלי קשר ל-`inbox` — נצפה בלוגים בזמן שהמשתמש שלח הקלטת בדיקה. סוטה מהעיצוב המקורי, לא נפתר.
- **תקרית פרטיות קלה, טופלה בזמן אמת:** לוג דיבאג זמני (שהוסר) הדפיס לרגע תוכן מלא של webhook events מ**קבוצות אחרות** של המשתמש (לא רק הצ'אט הייעודי) — כולל שמות ותוכן הודעות של צדדים שלישיים — כי ה-webhook הגלובלי מקבל את כל תעבורת ה-WhatsApp, והפילטר שלנו מתעלם מהשאר רק *לאחר* קליטה. קובץ לוג מקומי שהכיל את התוכן הזה נמחק מיד לאחר האיתור; המשתמש עודכן בזמן אמת.
- **בדיקת קצה-לקצה חיה הצליחה:** הודעת טקסט אמיתית שנשלחה לצ'אט "הודעה לעצמי" נקלטה נכון ב-SQLite (`type=text`, `direction=outgoing`, `body` נכון), כולל דדופ נכון על webhook כפול (WAHA שולח כל אירוע פעמיים בפועל).
