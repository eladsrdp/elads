# Orian CourierExpert™ API — אינטגרציית שילוח

## Overview
מסמך API חיצוני (Orian CourierExpert™, גרסה 1.4) לאינטגרציה עם מערכת השילוח של Orian — יצירת הזמנות הובלה (Home Delivery), הדפסת תוויות, מעקב סטטוס חבילות, ואיתור נקודות PUDO (חנויות/לוקרים). המסמך והדוגמאות המקוריות נמצאים מחוץ לריפו, ב-OneDrive: `דוקומנטציות/API description.docx` + 2 קבצי XML לדוגמה (One Package / MultiPackage to One Order). **סטטוס: 4 הקריאות המרכזיות (Login, CreateTransportationOrder, GetPackageStatus, GetTransporttaionOrderLabel) אומתו חי מקצה לקצה בהצלחה מלאה מול test environment; רק GetPudos לא נבדק. אין עדיין קוד אינטגרציה בפרויקט (בדיקות עד כה דרך Postman/Make בלבד).**

**Base URLs:** Test = `https://disapiTest.orian.com`, Production = `https://disapi.orian.com`.

**Endpoints (כולם אומתו חי מלבד GetPudos):** `Login` (POST, Basic Auth → AuthToken בתוקף לשעה, בגוף header לא ב-body), `Logout` (POST), `CreateTransportationOrder` (POST, גוף XML גולמי), `GetTransporttaionOrderLabel` (POST, **חריג**: גוף `x-www-form-urlencoded` אמיתי/מקודד — Key ריק, XML מקודד ב-Value — לא XML גולמי כמו שאר הקריאות; `ORDERID`=`REFERENCEORDER` בדיוק כמו שהמסמך תיאר, מחזיר `LABEL` כ-PDF ב-Base64), `GetPackageStatus` (GET, query params), `pudo/Getpudos` ו-`pudo/Getpudosjson` (GET, איתור PUDO לפי עיר/כתובת/מרחק, טרם נבדק).

CONSIGNEE (מספר לקוח קבוע אצל Orian) בדוגמאות: `30000060`.

**מודל בעלות המזהים** (לפי המסמך): `CONSIGNEE` מוקצה מראש ע"י Orian (קבוע). `TRANSPORTATIONORDERID` "Auto generated by Orian systems" — משאירים ריק, טרם אומת שחוזר בתגובה בפועל. `REFERENCEORDER`/`REFERENCEORDER2`/`HOSTORDERID` הם מספרי ההזמנה **של הלקוח** (בעתיד: מפריוריטי) — לא מונפקים ע"י Orian. `PACKAGEID` (ברקוד חבילה, עד 11 תווים אם מדפיסים תווית) — גם הוא באחריות הלקוח, אלא אם משתמשים ב-`CREATEPACKAGES`+`USEPACKREFERENCE` (שדות שלא נבדקו עדיין) שמאפשרים לאוריין להקצות מספור אוטומטי תחת ה-REFERENCEORDER במקום לספק PACKAGEID ידנית לכל חבילה. בבדיקות עד כה כל המזהים (REFERENCEORDER/HOSTORDERID/PACKAGEID) הומצאו ידנית עם סיומת timestamp לייחודיות, בהיעדר מערכת ERP מחוברת שמנפיקה מספרים אמיתיים.

## Open Questions
- שאר הקריאות (GetPudos) עדיין לא נבדקו חי.
- אין עדיין credentials (username/password) שמורים ב-.env — כשתתחיל אינטגרציה בקוד, יש להוסיף `ORIAN_USERNAME`/`ORIAN_PASSWORD` ל-.env (לא לצ'אט/git), ראו [[env-config]].
- לא ידוע אם זו אינטגרציה עצמאית חדשה או קשורה לפרויקט קיים (למשל priority-lite) — לברר עם המשתמש כשיתחיל פיתוח בפועל.
- כללי ייחודיות (uniqueness) של `PACKAGEID`/`REFERENCEORDER` בסביבת ה-test מול Orian לא ידועים במדויק — פותר בפועל ע"י תוספת סיומת ייחודית (timestamp) לכל ניסיון, ועם `PACKAGEID` בן 11 תווים בדיוק (המגבלה המתועדת) ההזמנה הצליחה.
- תגובת ה-`CreateTransportationOrder` המוצלחת מחזירה שדות שלא מתועדים במסמך כלל: `CARRIER`, `DELIVERYMETHOD`, `EXTERNALCHUTE`, `PIN` — לא ידוע אם אלו קבועים או משתנים לפי כתובת/סוג הזמנה.
- **נסגר (2026-09-08) ✅: `GetTransporttaionOrderLabel` עובד באופן מלא ומאומת.** דורש גוף `x-www-form-urlencoded` אמיתי (Key ריק, XML מקודד ב-Value) — **בניגוד** ל-Login/CreateTransportationOrder/GetPackageStatus שעובדים עם XML גולמי (אותו Content-Type מוצהר בכולם, מימוש שרת שונה מאחורי הקלעים). עם `ORDERID=REFERENCEORDER` (בדיוק כמו שהמסמך תיאר) והקידוד הנכון — התקבל `SUCCESS:true`, `STATUSCODE:200`, ו-`LABEL` עם PDF תקין ב-Base64 (מאומת: מתחיל ב-`JVBERi0` = חתימת PDF תקנית). "התקלה" שיוחסה בטעות ל-Orian (3 כשלים קודמים) הייתה טעות קידוד גוף מהצד שלנו בלבד.
- **פתוח: איך משחזרים את הקידוד הנכון במייק** — טבלת ה-x-www-form-urlencoded של מייק מחייבת Name (לא ניתן להשאיר ריק כמו בפוסטמן), בניגוד לפוסטמן. שתי גישות אפשריות טרם נבדקו בפועל: (1) לתת Name שרירותי (למשל "data") ולקוות ש-Orian קורא לפי מיקום/ערך ולא לפי שם השדה. (2) לחזור ל-Body content type=Custom ולבנות ידנית את המחרוזת המדויקת (`=` + `encodeURL(XML)`) בעזרת פונקציית ה-IML `encodeURL()` של מייק.
