# ניהול משימות (CUSTNOTESA) מסונכרן עם פריוריטי — עיצוב

## הקשר

priority-lite כבר תומך חלקית ב"משימות לקוח" (CUSTNOTESA בפריוריטי, ראה [[priority-lite-app]] ב-vault, session log 2026-06-16): אפשר ליצור משימה חדשה מתוך פרויקט נבחר, לראות משימות פתוחות של אותו פרויקט, ולקשר דיווח שעות למשימה ספציפית (`custnoteId`). מה שחסר: מסך פרטי משימה, עדכון (סטטוס/עדיפות/תיאור), העברה בין אנשי צוות, וחיפוש/רשימה גלובליים ("המשימות שלי", חיפוש בכל החברה).

הבקשה המקורית כללה גם סאב-משימות/טיוטות מקומיות שלא מסונכרנות עם פריוריטי בכלל. בגלל היקף הבקשה הכולל, הוחלט (ב-brainstorming) **לפצל לשני שלבים עצמאיים**. המסמך הזה מכסה **רק את Phase 1** — כל מה שמסונכרן עם פריוריטי. Phase 2 (סאב-משימות מקומיות) יקבל מסמך עיצוב נפרד בעתיד.

## מטרה

לאפשר בתוך priority-lite: יצירת משימה, מסך פרטי משימה (תקציר + עריכה), שינוי סטטוס, העברת משימה לאיש צוות אחר, חיפוש משימות בכל החברה, תצוגת "המשימות שלי", והיסטוריית שינויי סטטוס — הכל מסונכרן עם CUSTNOTESA בפריוריטי.

## מה בכוונה לא נכלל (Non-goals)

- **סאב-משימות/טיוטות מקומיות** (לא מסונכרנות) — Phase 2, מסמך עיצוב נפרד. לעולם לא ייכתבו לפריוריטי.
- **תשתית שירות-שטח** (`NGV_CUSTNOTE`: GPS כניסה/יציאה, ניווט) — נבדקה, לא רלוונטית לשימוש הפנימי של הצוות.
- **מנוע חוקי-מעבר סטטוס** — `NGV_NEXTSTATUS` הוא רשימת סטטוסים עם אייקון (למובייל), לא אכיפת מעברים חוקיים. האפליקציה לא תאכוף סדר מעברים; כל אחד מ-6 הסטטוסים הנבחרים ניתן לבחירה בכל שלב.
- **יצירת פרויקט/לקוח חדש** — יצירת משימה עדיין דורשת פרויקט קיים, נבחר דרך `TaskPicker` הקיים.
- **בדיקות אוטומטיות מול פריוריטי אמיתי** — ה-mock מספיק ל-CI; אימות חי הוא צעד ידני חד-פעמי בתחילת המימוש.

## מסכים וזרימת משתמש

**טאב חדש "משימות"** בניווט התחתון, עם שני מצבי תצוגה:
- **"שלי"** (ברירת מחדל) — משימות שה"לטיפול" בהן = המשתמש המחובר
- **"הכל"** — חיפוש חופשי על פני כל החברה, עם פילטר סטטוס

**מסך פרטי משימה** (לחיצה על פריט ברשימה):
- כותרת (`SUBJECT`), לקוח/פרויקט, שעות שדווחו (קיים כבר)
- סטטוס — בורר מתוך 6 הערכים (`TaskStatus`)
- עדיפות (0-99), תאריך יעד
- תיאור — שדה טקסט שמוסיף רשומה חתומה+מתוארכת חדשה בכל שמירה (לא עריכה חופשית של טקסט קיים — ראה סיכון #3)
- אחראי משימה — לצפייה בלבד
- לטיפול — בורר החלפה, מתוך עובדי priority-lite בלבד
- היסטוריה — רשימה מתקפלת מ-`DOCTODOLISTLOG` (תאריך, סטטוס, לטיפול, יוזם)

**יצירת משימה חדשה** — מרחיב את הטופס הקיים (כיום פתוח רק מתוך `ManualEntryModal` בהקשר פרויקט ספציפי) עם נקודת כניסה נוספת מהטאב "משימות" עצמו; עדיין דורש בחירת פרויקט/לקוח דרך `TaskPicker` הקיים.

## ארכיטקטורה

הרחבה של השכבות הקיימות, לא ארכיטקטורה מקבילה:

- **Adapter**: מתודות חדשות ב-`PriorityAdapter` (ממומשות ב-`odata.ts` וב-`mock.ts`), לצד הקיימות (`listCustNotes`, `createCustNote`).
- **Routes**: namespace חדש `/api/custnotes` (פעולות גלובליות — חיפוש, פרטי משימה, עדכון) בנפרד מ-`/api/tasks/:id/custnotes` הקיים (יצירה בהקשר פרויקט, נשאר ללא שינוי לצורך זרימת דיווח השעות).
- **Client**: טאב חדש "משימות" בניווט התחתון (רשימה + פילטרים), מסך פרטי משימה חדש, ובורר עובד חדש (`GET /api/employees`, שולף מ-Supabase/whitelist — שם + `priorityEmpId` בלבד, בלי טלפון/`totp_secret`).

## מודל הנתונים

הרחבת `CustNote` הקיים (`shared/src/types.ts`):

```ts
interface CustNote {
  // קיים: id, subject, custName, custDes, statDes, tillDate, projDocNo, hoursReported
  priority?: number               // PRIO (0-99)
  description?: string            // CUSTNOTESTEXT_ONE.TEXT — התוספת האחרונה
  ownerName?: string              // ZRDP_TASKOWNER ("אחראי משימה") — לצפייה בלבד
  handlerEmpId?: string           // "לטיפול" — שם שדה מדויק טרם מאומת, ראה סיכונים
  handlerName?: string
  history?: TaskStatusLogEntry[]  // מ-DOCTODOLISTLOG, read-only בפריוריטי
}

interface TaskStatusLogEntry {
  date: string
  status: string
  handlerName?: string
  initiatorName?: string
}

interface UpdateCustNoteInput {
  status?: TaskStatus              // אחד מ-6 הערכים (ראה טבלה)
  priority?: number
  tillDate?: string
  handlerEmpId?: string
  description?: string             // תוספת חדשה, לא עריכת קיים
}

type TaskStatus = 'טיוטא' | 'לפיתוח' | 'לבדיקת פיתוח' | 'בוצעה' | 'מבוטלת' | 'במעקב'
```

**מתודות אדפטר חדשות**:
- `searchCustNotes(query, filters: { mine?: boolean; status?: TaskStatus[] }, limit)` — חיפוש גלובלי (בניגוד ל-`listCustNotes` הקיים, המוגבל ללקוח אחד)
- `getCustNoteDetail(id)` — כולל `description` + `history`
- `updateCustNote(id, changes: UpdateCustNoteInput)`
- `listEmployees()` — לבורר "לטיפול"

**Routes חדשים**:

| Method | Path | תיאור |
|---|---|---|
| GET | `/api/custnotes?q=&mine=&status=` | חיפוש גלובלי |
| GET | `/api/custnotes/:id` | פרטי משימה + היסטוריה |
| PATCH | `/api/custnotes/:id` | עדכון (סטטוס/עדיפות/תאריך/לטיפול/תיאור) |
| GET | `/api/employees` | רשימת עובדי priority-lite לבורר "לטיפול" |

## שדות פריוריטי שזוהו

| שדה באפליקציה | ישות/שדה בפריוריטי | הערה |
|---|---|---|
| סטטוס | `CUSTNOTESA.STATDES` | **דורש אימות כתיבה חי** — לא ברור אם כתיבה ישירה עובדת (ראה סיכונים) |
| עדיפות | `CUSTNOTESA.PRIO` | Int64, 0-99 |
| תאריך יעד | `CUSTNOTESA.TILLDATE` | כבר בשימוש ביצירה |
| תיאור | `CUSTNOTESTEXT_ONE.TEXT` (sub-form `CUSTNOTESTEXT_ONE_SUBFORM`) | שדות נלווים `APPEND`/`SIGNATURE` — **סמנטיקת POST דורשת אימות** |
| אחראי משימה | `CUSTNOTESA.ZRDP_TASKOWNER` | לצפייה בלבד |
| לטיפול | טרם מאומת — מועמד: `CUSTNOTESA.USERLOGIN` | **דורש אימות** — היום USERLOGIN מוגדר כ"יוצר" בקוד הקיים |
| היסטוריית סטטוס | `DOCTODOLISTLOG_SUBFORM` (`Collection(DOCTODOLISTLOG)`) | כל השדות read-only — קריאה בלבד, אין סיכון כתיבה |

## זרימת עדכון

עדכון סטטוס/עדיפות/לטיפול מה-UI מבצע **optimistic update** מקומי (מציג את הערך החדש מיד), שולח `PATCH` לשרת, ובמקרה כשל — מחזיר את הערך הקודם (rollback), באותו דפוס כמו טיוטות דיווח שעות שחוזרות ל-`draft` בכשל רשת.

בחירת "לטיפול" מוגבלת לרשימת עובדי priority-lite: חסימה בצד לקוח (select מוגבל) **וגם** אימות zod בצד שרת מול רשימת `priorityEmpId` חוקיים — לא סומכים על הקליינט בלבד.

## טיפול בשגיאות

| מצב | התנהגות |
|---|---|
| כתיבת שדה נעולה בפריוריטי (כמו PARTNAME/PDES בעבר) | הודעת שגיאה נקייה (`extractErrorMessage` הקיים), rollback לערך הקודם |
| `handlerEmpId` לא ברשימת העובדים החוקיים | נדחה ב-zod, `400` עם הודעה ברורה |
| כשל רשת בעדכון בודד | rollback + הודעת "אין חיבור לשרת", אין אובדן מידע (הערך הקודם עדיין מוצג נכון) |
| משימה לא נמצאה (`:id` שגוי) | `404` |

## בדיקות

- הרחבת `mock.ts` עם כמה רשומות CUSTNOTE מדומות **על פני כמה לקוחות שונים** — כדי לבדוק חיפוש גלובלי, לא רק פר-פרויקט כמו היום.
- בדיקות unit ל-actions החדשים: סכמת zod של `updateCustNote` (סטטוס מוגבל ל-6 ערכים, `handlerEmpId` מוגבל לעובדים קיימים).
- בדיקות client ללוגיקת פילטור "שלי"/"הכל" ופילטר סטטוס (לוגיקה טהורה, לא Dexie — כמו בפיצ'ר היעד/שעות, אין תשתית fake-indexeddb בפרויקט).
- **בדיקה חיה חד-פעמית** (לא בחבילת האוטומציה): סקריפט גילוי קטן שכותב וקורא מול משימת בדיקה אמיתית בפריוריטי, מאמת את שלושת הסיכונים למטה, ומנקה אחריו. המשתמש אישר יצירת משימה חיה לבדיקות (2026-08-17).

## סיכונים טכניים — לפתור כצעד ראשון בתוכנית המימוש

לא ניתן לדעת מהמטא-דאטה בלבד (בדיוק כמו הפתעת PARTNAME/PDES בדיווחי שעות בעבר) — צריך סקריפט גילוי קטן מול פריוריטי אמיתי, **לפני** בניית מסך אחד:

1. **כתיבת סטטוס** — האם `PATCH`/`POST` ישיר ל-`STATDES` עובד, או שיש נעילה סמויה שדורשת נתיב אחר?
2. **שדה "לטיפול" בפועל** — איזה שם שדה מדויק על `CUSTNOTESA` עצמו מייצג את "לטיפול" מהצילום שסופק — צריך לאמת מול נתונים אמיתיים (לא רק שם שדה מהמטא-דאטה).
3. **סמנטיקת תיאור** — `CUSTNOTESTEXT_ONE` עם `APPEND`/`SIGNATURE`: האם POST מוסיף רשומה חדשה חתומה (כמו בתצוגת "תקציר המשימה" שנצפתה בפריוריטי), או דורס טקסט קיים?

## מה נדחה בכוונה

- **Phase 2 — סאב-משימות/טיוטות מקומיות**: צ'קליסט תחת משימה אמיתית + טיוטות חופשיות עצמאיות, שתיהן לצמיתות לא מסונכרנות עם פריוריטי. מסמך עיצוב נפרד.
- **תצוגת אייקוני סטטוס** (`NGV_NEXTSTATUS`) — שיפור עתידי אפשרי, לא נדרש ל-v1 התפקודי.
- **אכיפת מעברי סטטוס חוקיים** — לא נמצא מנגנון כזה בפריוריטי; לא ייבנה גם באפליקציה.
